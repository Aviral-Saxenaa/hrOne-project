# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | Grace period logic truncates to integer before comparing (`minutes > 10`), causing an off-by-one bug at 10 minutes and 1 second. Also fails to truncate input timestamps to whole seconds (Rule R1) and does not account for timezones (assumes naive datetime instead of IST). | With shift start `09:30`, punching in at `09:40:01` IST yields elapsed time of 10 min 1 sec. `int(601 / 60)` evaluates to `10`, failing `minutes > 10` and returning `0` instead of `10` (Rule R2). | Truncated instant to whole seconds, converted to IST, computed elapsed seconds `(punch_in - shift_start).total_seconds()`, and returned `int(elapsed_seconds // 60)` if `elapsed_seconds > 600` else `0`. |
| 2 | `compute_work_hours` (lines 40-41) | Uses Python's standard `round(..., 2)` which performs round-half-to-even (banker's rounding) rather than standard mathematical round-half-up (Rule R4). | Punch in `09:00:00`, punch out `11:07:30` (7,650 seconds = 2.125 hours). `round(2.125, 2)` produces `2.12` instead of the expected `2.13`. | Implemented `Decimal` division quantized with `ROUND_HALF_UP` to two decimal places: `Decimal(diff_seconds) / Decimal(3600)`. |
| 3 | `compute_overtime` (lines 44-48) | Missing minimum 30-minute threshold requirement (Rule R3). Any positive duration is counted as overtime. Additionally, for overnight shifts (`shift_end <= shift_start`), `end` is constructed on `date_str` rather than the following calendar day. | Punching out at `18:45` for an `18:30` shift end (15 minutes elapsed) returns `15` instead of `0`. On overnight shifts, calculates negative or erroneous offsets. | Adjusted shift end date by +1 day for overnight shifts (`shift_end <= shift_start`), computed elapsed minutes, and returned `minutes` only if `minutes >= 30` else `0`. |
| 4 | `create_employee` (lines 78-85) | Check-then-insert race condition (`if db.employees.find_one(...)`). Under concurrent requests with the same `emp_code`, both checks can succeed, causing duplicate inserts. | Two simultaneous `POST /employees` requests with identical `emp_code` both return 201 Created instead of one 201 and one 409. | Enforced database-level unique index on `emp_code` and caught PyMongo `DuplicateKeyError` to return HTTP 409 Conflict. |
| 5 | `create_employee` (lines 53-61, 78-85) | Missing validation that `shift_start` must differ from `shift_end` as specified in the API contract. | Sending `POST /employees` with `shift_start: "09:30"` and `shift_end: "09:30"` returns 201 Created instead of 422 Unprocessable Entity. | Added Pydantic model validation verifying `shift_start != shift_end`, raising 422 on violation. |
| 6 | `list_employees` (line 93) | Pagination offset calculation uses `skip = page * page_size`, which skips `page_size` records on `page = 1`. | Requesting `GET /employees?page=1&page_size=20` returns employees 21 to 40; the first 20 employees are skipped and never accessible. | Corrected offset formula to `skip = (page - 1) * page_size`. |
| 7 | `list_employees` (line 94) | `total` count query ignores the `department` filter, using `db.employees.count_documents({})`. | `GET /employees?department=Engineering` returns filtered records in `items`, but `total` reports the total count of the entire collection across all departments (violating Rule R10). | Updated count query to use the applied filter: `db.employees.count_documents(q)`. |
| 8 | `list_employees` (line 95) | Query lacks explicit sorting. The API contract requires results sorted by `emp_code` ascending. | Consecutive queries or sharded clusters return employees in non-deterministic natural insertion order. | Added `.sort("emp_code", 1)` to the cursor. |
| 9 | `punch_in` (lines 101, 113) | Unhandled `None` when `emp_code` does not exist. `emp["shift_start"]` raises an unhandled `TypeError`. | Calling `POST /attendance/punch-in` with a non-existent `emp_code` returns HTTP 500 Internal Server Error instead of 404 Not Found. | Added explicit lookup verification: if employee not found, raise HTTP 404 Not Found. |
| 10 | `punch_in` (lines 102-104) | System-local timezone used instead of IST, and lacks overnight shift boundary resolution (Rule R1). | For overnight shift (22:00 - 06:00), punching in at `01:00` IST on July 7 is assigned to `2026-07-07` instead of `2026-07-06`. Also uses server clock instead of UTC when `punched_at` is omitted. | Converted instants to IST, checked whether shift is overnight and time is before `shift_end`, and assigned the attendance date to the previous calendar day when applicable. |
| 11 | `punch_in` (lines 104-106, 118) | Check-then-insert race condition for identical `(emp_code, date)`. | Two concurrent punch-in requests at the same instant both pass `find_one` and create duplicate logs for the same day. | Created a unique compound index on `{"emp_code": 1, "date": 1}` and caught `DuplicateKeyError` to return HTTP 409 Conflict. |
| 12 | `punch_in` (lines 119-121) | Response leaks internal MongoDB `_id` as `id` and outputs Python `datetime` objects instead of epoch milliseconds integers. | Response violates OpenAPI schema contract for `AttendanceRecord`, which forbids `id` and requires epoch milliseconds integers for instant fields. | Standardized response mapping to serialize instants as integer epoch milliseconds and omitted `_id`/`id`. |
| 13 | `punch_in` (lines 63-67, 100) | Missing validation for `status` and `punched_at`. Accepts invalid statuses like `ABSENT` or `LEAVE` via punch-in, and accepts timestamps outside allowed millisecond range. | Punching in with `status: "LEAVE"` or `punched_at: 1720000000` (seconds instead of ms) succeeds with 201 instead of 422. | Restricted status to `PresenceStatus` (`PRESENT`, `WFH`, `ON_DUTY`) and enforced epoch ms bounds (`100000000000 <= punched_at <= 4102444800000`). |
| 14 | `list_attendance` (lines 144-147) | In-memory loading and sorting of full collection (`docs = list(db.attendance_logs.find(q))`). | Querying across ~100,000 documents causes severe memory consumption, slow responses, and potential process crash. Also omits secondary sort by `emp_code` ascending. | Delegated filtering, sorting, and pagination directly to MongoDB cursor with compound index support: `.sort([("date", -1), ("emp_code", 1)]).skip((page - 1) * page_size).limit(page_size)`. |
| 15 | `list_attendance` (lines 137-142) | Missing date range validation when `date_from > date_to`. | `GET /attendance?date_from=2026-07-15&date_to=2026-07-01` returns 200 OK with empty items instead of HTTP 422. | Added explicit validation check: `if date_from and date_to and date_from > date_to: raise HTTPException(422)`. |
| 16 | `health` (lines 72-74) | Returns `{"status": "ok"}` without testing database connectivity. | When MongoDB is stopped, `/health` still returns 200 OK instead of HTTP 503 Service Unavailable. | Added `client.admin.command('ping')` health check with try/except, returning HTTP 503 if unreachable. |
| 17 | Startup indexes (missing) | No indexes defined or created at startup. | At scale (~100k records), queries and listings perform full collection scans (`COLLSCAN`), causing timeout and performance degradation. | Added idempotent startup index creation for `employees` and `attendance_logs`. |

Also note anything you looked at and decided was **not** a defect, and why:
- `IST = timezone(timedelta(hours=5, minutes=30))`: Correct representation of Indian Standard Time (+05:30) constant across all calculations.
- Using `emp_code` as primary business identifier rather than MongoDB's `_id`: Correctly adheres to the specification in `DATA_MODEL.md` where `emp_code` is the human-facing immutable customer identifier.
- Returning `null` for `work_hours` on incomplete records: Correct per Rule R4 and `DATA_MODEL.md` (unclosed records before punch-out must have `work_hours: null`).
